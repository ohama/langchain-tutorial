# SQLite 체크포인터와 프로세스 재시작

## 개념: 왜 필요한가

`InMemorySaver`는 프로세스가 끝나면 사라진다. 실제 에이전트는 껐다 켜도 하던 일을 이어가야 한다. `SqliteSaver`는 같은 상태를 파일에 저장하므로 프로세스가 바뀌어도 `thread_id`만 같으면 이어진다.

왜 "같은 프로세스 안에서 `SqliteSaver` 인스턴스를 새로 만드는 것"으로는 증명이 안 될까 — 그건 재시작이 아니기 때문이다. 그래서 이 장은 진짜로 파이썬 프로세스를 두 번 띄운다. 스키마는 첫 사용 시 자동으로 만들어지고, WAL 모드라 사이드카 파일이 함께 생긴다.

- `subprocess.run([sys.executable, ...])`가 워커를 별도의 OS 프로세스로 만든다 — 같은 인터프리터 안에서 객체를 새로 만드는 것과 다르다.
- 시작과 종료 시점에 DB 파일과 WAL 사이드카(`-wal`, `-shm`)를 모두 지워서, 실행할 때마다 같은 결과가 나오게 한다.
- 경로와 프로세스 번호는 출력하지 않는다 — 둘 다 실행 환경마다 달라지는 값이라 캡처를 재현 불가능하게 만들기 때문이다. 대신 부모가 자신의 pid를 인자로 넘기고, 워커는 그 값과 비교한 결과(`부모 프로세스와 동일: False`)만 출력한다.

실행 방법 (examples 디렉터리에서):

```bash
uv run python ch04_langgraph/04_sqlite_checkpoint.py
```

`=== 1 ===`에서는 시작 전에 DB 파일이 없었다(`시작 전 DB 파일 존재: False`). `=== 2 ===`에서 첫 번째 프로세스(`run1`)가 "내 이름은 철수야. 기억해줘."를 보냈고, 실행 후에는 DB 파일이 생겨 있었다(`실행 후 DB 파일 존재: True`). 이번 캡처에서는 모델이 곧바로 답하지 않고 재고 조회 도구를 한 번 부른 뒤(존재하지 않는 품목이라 오류가 났다) 이름을 확인했다는 안내로 답했는데, 이 과정에서 메시지가 4개(질문, 도구 호출, 도구 오류, 최종 답) 쌓였다.

`=== 3 ===`에서 완전히 새로운 파이썬 프로세스(`run2`)가 같은 `thread_id="restart-demo"`로 "내 이름이 뭐라고 했지?"를 물었고, 이번에는 곧바로 "당신의 이름은 **철수**라고 하셨어요!"로 답했다 — 첫 번째 프로세스가 SQLite 파일에 저장한 이름을 두 번째 프로세스가 그대로 읽어냈다는 뜻이다. 이 스레드에 쌓인 메시지 수는 6으로, `run1`이 끝났을 때의 4보다 늘어나 있다. 두 워커 모두 `부모 프로세스와 동일: False`를 찍었다(정확히 두 번) — 워커가 실행기와 다른 진짜 별도 프로세스였다는 뜻이다.

`=== 4 ===`에서 정리 후 DB 파일이 다시 사라졌다(`정리 후 DB 파일 존재: False`) — 이 예제는 실행할 때마다 깨끗한 상태에서 시작하고 끝난다.

## 요점 정리

- `SqliteSaver.from_conn_string(db_path)`는 컨텍스트 매니저이고, 스키마는 첫 사용 시 자동으로 만들어진다.
- `InMemorySaver`와 달리 상태가 파일에 남으므로, 프로세스가 완전히 바뀌어도 같은 `thread_id`면 대화가 이어진다.
- 이번 캡처에서 두 번째 프로세스는 `부모 프로세스와 동일: False`를 찍었고, 첫 번째 프로세스가 저장한 이름("철수")을 그대로 답했다 — 진짜 재시작을 견뎠다는 증거다.
- WAL 모드라 DB 파일 하나에 `-wal`/`-shm` 사이드카가 따라오므로, 정리할 때 셋 다 지워야 한다.
- 경로·프로세스 번호 같은 실행 환경마다 달라지는 값은 출력하지 않고, 비교 결과(불리언)만 출력해야 캡처가 재현 가능하다.
