# 도구 정의와 bind_tools

## 개념: 왜 필요한가

LLM은 정확한 사칙연산이나 실시간 데이터(예: 창고 재고 시스템)에 직접 접근할 수 없다. 모델이 직접 숫자를 계산하거나 데이터베이스를 조회하게 만드는 대신, 모델에게 "이 작업이 필요하면 이런 이름과 인자로 요청해라"라는 도구 목록을 알려주고, 실제 실행은 우리 코드가 맡는 방식이 도구 호출(tool calling)이다. 모델은 아무것도 직접 실행하지 않는다 — 구조화된 요청(도구 이름 + 인자)만 돌려줄 뿐이다.

이 메커니즘은 사실 낯설지 않다. 1부 5장에서 본 `get_structured_model`의 `function_calling` 방식이 이미 같은 통로를 썼다 — 스키마를 도구 정의처럼 모델에 전달해 모델이 그 "도구"를 호출하는 형태로 필드를 채우게 한 것이다. 이 장에서는 그 메커니즘을 도구 호출 그 자체로 정면으로 다룬다.

세 가지 개념이 핵심이다.

- `@tool`: 타입 힌트가 있는 파이썬 함수를 도구로 승격시킨다. 타입 힌트는 입력 스키마의 근거가 되고, docstring은 도구 설명이 된다.
- `bind_tools`: 모델에 도구 스키마 목록을 결합해 새 러너블을 만든다. 이후 모든 요청에 도구 정의가 함께 전송된다.
- `AIMessage.tool_calls`: 모델이 도구를 쓰기로 했을 때, 응답에 담기는 `name`/`args`/`id`/`type`을 가진 요청 목록이다.

아래는 저자가 로컬 `flashnext` 모델로 실제 실행해 캡처한 결과다. LLM 응답이므로 여러분의 결과와 글자 단위로 같지 않을 수 있다.

```text
{{#include ../../../outputs/ch02_tools/01_define_tools.out:2:}}
```

`=== 1 ===`에서 세 도구 모두 타입 힌트만으로 정확한 JSON 스키마(`{"a": {"title": "A", "type": "integer"}, ...}`)가 자동 생성된 것을 볼 수 있다. `=== 2 ===`는 `finish_reason: tool_calls`와 함께 `add({"a": 7, "b": 5})` 하나를 요청했고, 이번 캡처에서는 `content`에도 `'7 + 5 = **12**'`라는 텍스트가 함께 담겼다. `=== 3 ===`은 한 번의 응답에 `lookup_stock` 호출 두 개(사과, 바나나)가 리스트에 함께 담겨 왔다 — 별도의 파싱 없이 병렬 호출이 그대로 리스트로 온다. `=== 4 ===`는 도구가 필요 없는 질문에 `finish_reason: stop`, `tool_calls: 0개`로 응답했다 — 모델이 도구를 쓸지 말지는 우리가 강제한 것이 아니라 모델 스스로 판단한 결과다.

아직 어떤 도구도 실제로 실행되지 않았다는 점이 중요하다. 모델은 "이렇게 호출해 달라"고 요청만 했을 뿐이다. 다음 장에서 이 요청들을 실제로 실행하고 결과를 모델에 다시 돌려주는 루프를 만든다.

## 요점 정리

- `@tool` + 타입 힌트 + 한글 docstring만으로 이름/설명/입력 스키마가 모두 자동 생성된다.
- `bind_tools([...])`는 모델에 도구 스키마를 결합한 새 러너블을 만든다.
- `AIMessage.tool_calls`는 모델이 도구 호출을 요청했을 때 담기는 `name`/`args`/`id`/`type` 목록이며, 병렬 호출도 그대로 리스트로 온다.
- 모델이 도구를 쓸지 말지는 질문 내용에 따라 모델이 스스로 결정한다.
- 도구 호출 시점에는 아무 도구도 실행되지 않는다 — 실행은 우리 코드의 몫이다.
